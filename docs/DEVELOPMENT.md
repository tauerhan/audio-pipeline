# Работа с проектом

## Две среды

Каноническая рабочая папка — Ubuntu: `/home/esmirnov/audio-pipeline`.
Windows-папка подготовки содержит код и документацию, но не рабочий конфиг,
окружение или архив. После первой публикации используйте обычные clone/pull,
а не постоянное двустороннее копирование файлов.

Git remote: `git@github.com:tauerhan/audio-pipeline.git`.
До публикации проверить `git status --short`, `git diff --cached --stat`
и отсутствие приватных данных в индексе.
.gitignore не удаляет уже закоммиченные секреты из истории.

## GitHub

- Небольшую задачу описывать через шаблон Issue: результат, ограничения, приёмка.
- Для дальнейших изменений использовать отдельную ветку и Pull Request.
- Лёгкий CI проверяет репозиторий при push/PR.
- Не подключать рабочую ВМ как общедоступный self-hosted runner.
- Полное распознавание и оценка качества выполняются локально на копиях данных.
- GitHub-hosted CI не должен получать аудио, заметки, пути архива или SSH-ключи.
- Публичность репозитория и лицензия — отдельные решения владельца.

## Как ставить задачу Codex

Пример первого поручения:

> Прочитай AGENTS.md, PROGRESS.md, docs/AUDIT.md и F01 в feature_list.json.
> Реализуй загрузку и валидацию конфигурации до любых операций записи.
> Сделай --dry-run и --list неизменяющими. Сохрани существующие CLI.
> Проверь на временных каталогах и синтетических данных; рабочий архив не трогай.
> Покажи результат проверки и обнови PROGRESS.md.

Для сложного этапа сначала составить короткий план в docs/plans/.
На одну задачу достаточно цели, входных условий, запретов и измеримой приёмки.
Не нужно вставлять весь курс Harness_ru в каждый запрос или AGENTS.md.

## Цикл работы

1. Прочитать текущее состояние и выбрать один пункт.
2. Проверить исходное поведение и определить способ приёмки.
3. Изменить минимально необходимый код.
4. Выполнить scripts/check.py и проверку изменённого поведения.
5. Записать ограничения и следующий шаг в PROGRESS.md.
6. По поручению владельца сделать коммит, отправить ветку и открыть PR.

Система пока не содержит набора поведенческих тестов. Их первый этап —
синтетические временные файлы, mocked ASR/Ollama и сценарии сбоев, а не
автоматическое распознавание личного архива. Успешная проверка структуры
не должна отмечать эти будущие сценарии выполненными.
